MCP Architecture Deep Dive: How It Really Works

12 min read • Published June 14 2025

Overview

The Model Context Protocol (MCP) provides a language-agnostic contract that lets an LLM-powered client discover, request, and manipulate resources exposed by an MCP server. While the surface area looks small—roughly a dozen JSON-RPC methods—the architecture behind it solves a surprisingly broad set of problems: capability scoping, streaming responses, multi-transport negotiation, and sandboxed execution. This deep dive unpacks each layer so you can design systems that are both secure and future-proof.

Core Components

Hosts

A host is the environment in which a server or client runs—think containers, local processes, or remote VMs. Hosts are responsible for sandboxing and can attach metadata such as CPU limits or network policies.

Servers

An MCP server exposes resources and tools. A resource could be a file, database table, or live API endpoint. Tools are executable operations (functions, scripts) that operate on resources. Servers declare capabilities using a JSON schema so clients can reason about them before invoking anything.

Clients

The client is typically an AI assistant. It connects to one or more servers via transports such as stdio (local CLI) or HTTP/SSE (remote). Clients send JSON-RPC requests, receive responses, and may stream incremental patches.

Transports

MCP decouples the message format (always JSON-RPC) from the transport. Today the reference implementation supports:

  • stdio – zero-config local integration
  • HTTP/SSE – stateless request/stream responses
  • WebSocket (draft) – bi-directional sessions for low-latency tools

Request/Response Data Flow

  1. Capability Discovery – Client calls server.getManifest.
  2. Resource Listing – Client issues resources.list; server responds with URIs and metadata.
  3. Tool Invocation – Client sends tools.exec with specific parameters; server may stream tool_patch events.
  4. Completion – Server returns final JSON result or error.

The spec guarantees idempotent retries for read-only methods, which unlocks automatic recovery for LLM hallucinations. Write-operations must include intentToken headers to guard against replay attacks.

{
  "jsonrpc": "2.0",
  "id": "abc123",
  "method": "tools.exec",
  "params": {
    "tool": "search_files",
    "args": ["*.py"],
    "intentToken": "sha256-..."
  }
}

Security Considerations

MCP's design acknowledges that AI agents can be unpredictable. Security is therefore baked into every layer:

  • Capability Scopes – Similar to OAuth scopes; clients request minimal access.
  • Sandboxed Execution – Tools run in separate OS processes or WASM runtimes.
  • Attestation – Future drafts include signed manifests for supply-chain integrity.

Servers should treat untrusted prompts like remote code. Practical measures include SELinux/AppArmor profiles, seccomp filters, and timeouts.

Reference Implementation Walkthrough

The TypeScript SDK exposes high-level classes:

import { Server, ListResourcesRequest } from '@modelcontextprotocol/sdk/server';

const server = new Server({ name: 'example', version: '0.1.0' });

server.setRequestHandler(ListResourcesRequest, async () => ({
  resources: [{ uri: 'file://README.md', name: 'README', mimeType: 'text/markdown' }]
}));

await server.connect();

With fewer than 20 lines you have an MCP-compatible service. The same code in Python via FastMCP is equally terse.

Frequently Asked Questions

How is MCP different from OpenAI Plug-ins?

Plug-ins require HTTPS endpoints and model-specific JSON manifests. MCP is transport-agnostic and model-agnostic.

Can I self-host an MCP server?

Yes. Reference implementations have no external dependencies.

Does MCP support streaming outputs?

Yes via SSE or WebSocket transports.

Is there a versioning strategy?

The spec follows semantic versioning; version field in the manifest signals breaking changes.
